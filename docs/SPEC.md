# Proposed Semantic Specification

This is a design document, not yet an implemented language specification.

## 1. Core concepts

### Refinement

A named relation connecting a concrete SPARK entity or state to an abstract model.

### Abstract model

A ghost-level mathematical view used by behavioral contracts. Initially this will normally be a SPARK functional container or a user-provided ghost type/function.

### Representation pattern

A reusable schema describing how a family of concrete representations maps to an abstract structure and what generic proof facts can be generated.

### Representation roles

Concrete entities filling pattern-defined roles, such as `storage`, `first`, `length`, and `capacity`.

### Generated obligation

A contract, assertion, lemma, or invariant emitted to establish/refine the abstraction. All generated obligations are subject to GNATprove unless explicitly documented as non-proof metadata.

## 2. Semantic authority

The project needs a clear hierarchy so automation cannot accidentally redefine intent.

Recommended authority order:

```text
1. User-authored public SPARK contracts and model semantics
2. User-authored refinement mapping
3. Pattern definition
4. Generated artifacts
5. Diagnostic suggestions
```

A generator must never silently modify level 1 to satisfy a proof.

## 3. Pattern compatibility

Before generation, the tool should validate structural conditions that can be checked semantically.

For `circular_sequence`, examples include:

- `storage` is an indexable bounded container/array of compatible element type;
- `first` is compatible with the storage index domain;
- `length` is discrete and nonnegative by type/contract;
- `capacity` can be related to storage length;
- the chosen abstract model is a sequence-like model;
- generated arithmetic can be expressed without introducing unchecked overflow assumptions.

A failed compatibility check is a tooling error, not a proof failure.

## 4. Generated facts versus generated suggestions

These must be distinct.

### Generated fact

An assertion the pattern claims follows from its semantics and expects GNATprove to prove.

### Suggested fact

A candidate invariant/lemma that might help a proof but is not guaranteed to be useful or even provable in the current context.

The CLI and source comments should distinguish them. Future AI/invariant synthesis belongs in the suggestion category unless the fact comes from a deterministic pattern rule.

## 5. No-assumption default

The default profile must reject generation of:

- `pragma Assume`;
- proof-only imported functions without a verified body when used as axioms;
- deliberately disabled checks that are necessary to establish a generated fact;
- arbitrary Why3 axioms;
- solver-specific trusted facts not represented in the project's reviewed foundation.

An advanced experimental mode might eventually support explicitly configured trusted foundations, but those must be visible in a machine-readable trust report and cannot be the normal workflow.

## 6. Generated provenance

Every generated declaration should identify:

- refinement ID;
- pattern ID and version;
- pattern rule ID;
- generator version;
- source entity/manifest location where practical.

Example:

```ada
--  Generated by spark-refine.
--  refinement: queue_contents
--  pattern: circular_sequence@1
--  rule: logical-index-in-range
```

This metadata makes code review and diagnostics substantially easier.

## 7. Operation schemas

Patterns may optionally understand common operations such as append, remove-first, allocate, release, set-bit, clear-bit, or transition.

The tool should avoid inferring behavior from procedure names. Operation semantics must be linked explicitly through source metadata or manifest declarations.

For example:

```toml
[[refinement.operation]]
entity = "Ring_Buffer.Push"
kind = "append"
value_parameter = "E"
```

The user's public postcondition remains authoritative. The operation schema tells the pattern what helper proof facts to generate.

## 8. Generated identifiers

Identifiers should be stable and namespaced to minimize collision:

```text
SR_<Refinement>_<Rule>
```

or contained in a generated proof package so shorter descriptive names are possible.

Names should describe mathematical meaning rather than implementation steps where possible.

## 9. Errors

CLI errors should distinguish categories:

```text
E1xx manifest/schema
E2xx Ada semantic resolution
E3xx pattern compatibility
E4xx generation conflict
E5xx drift
E6xx GNATprove integration
E7xx policy/trust violation
```

Machine-readable JSON output can expose stable error codes from the beginning even if human text evolves.

## 10. Versioning

The manifest has its own `format_version`.

Each pattern has a semantic version independent of the tool executable. A project can pin a pattern major version to prevent unexpected proof changes.

Generated artifacts should record the resolved pattern version so proof changes are auditable.
